# Codebase Patterns

Seeded from the design session on 2026-08-17. These are verified against source; trust them.

## Build and test commands
- Build (skip ITs): `./gradlew build -x :integ-test:integTest`
- Unit tests: `./gradlew test`
- All integration tests: `./gradlew :integ-test:integTest`
- Single IT class: `./gradlew :integ-test:integTest --tests "org.opensearch.sql.calcite.remote.CalciteDedupCommandIT"`
- Single IT method: `./gradlew :integ-test:integTest --tests "org.opensearch.sql.calcite.remote.CalciteExplainIT.testComplexDedup"`
- `-Dtests.security.manager=false` is already set in build.gradle.
- `:doctest:bootstrap` CANNOT run on this dev host: the repo venv is python3.7 and `doctest/sql-cli` pins `boto3==1.34.34`, which requires python>=3.8. `./gradlew build -x :integ-test:integTest` therefore FAILS on `:doctest:bootstrap` for reasons unrelated to any code change. Use `./gradlew build -x :integ-test:integTest -x :doctest:bootstrap -x :doctest:doctest` instead.
- Full Java build takes ~9 min cold; `./gradlew test` ~20s warm; `./gradlew spotlessCheck` ~35s.

## Settings that already exist — do not add new ones
- `plugins.calcite.enabled` → CALCITE_ENGINE_ENABLED
- `plugins.calcite.pushdown.enabled` → CALCITE_PUSHDOWN_ENABLED
- `plugins.calcite.fallback.allowed` → CALCITE_FALLBACK_ALLOWED
- Defined in `common/src/main/java/org/opensearch/sql/common/setting/Settings.java:42-47`
- The PoC posture is `pushdown.enabled=false` and `fallback.allowed=false`. This is a config flip, not new code.

## Plan-level limit already exists — do not add a second limit concept
- `QueryService.convertToCalcitePlan` (`core/src/main/java/org/opensearch/sql/executor/QueryService.java:1032-1036`) wraps every plan in `LogicalSystemLimit(QUERY_SIZE_LIMIT, querySizeLimit())`.
- `LogicalSystemLimit extends Sort`, so it has a `fetch` and is optimizer-visible.
- It is already matched by `LimitIndexScanRule` (`opensearch/src/main/java/org/opensearch/sql/opensearch/planner/rules/LimitIndexScanRule.java:24`).
- `plugins.query.size_limit` (`OpenSearchSettings.java:204`) falls back to `IndexSettings.MAX_RESULT_WINDOW_SETTING` = 10000.

## Explain goldens
- YAML files under `integ-test/src/test/resources/expectedOutput/calcite/`
- Loaded via `loadExpectedPlan("name.yaml")` at `PPLIntegTestCase:484`, asserted with `assertEquals`
- Re-baselining means editing the YAML
- THE DIRECTORY IS CHOSEN BY A CLUSTER-SETTING READ, and this bounds the blast radius of every staged-path output change: `loadExpectedPlan` (`PPLIntegTestCase:484`) calls `isPushdownDisabled()` (line 398), which reads the TRANSIENT `plugins.calcite.pushdown.enabled`. Enabled -> `expectedOutput/calcite/` (372 files). Disabled -> `expectedOutput/calcite_no_pushdown/` (167 files). Every `Staged*IT` class sets that setting false in `init()`, so staged output is asserted ONLY against `calcite_no_pushdown/`. An empty `git diff -- expectedOutput/calcite/` is therefore the load-bearing proof that a staged change left the production default untouched — quote it in every story that touches explain output.
- RE-BASELINING NEEDS A MECHANICAL ADDITIONS-ONLY GATE, declared before you start. A +/- line count is not a gate and a summary claim like "just trailing-newline normalization" has already been wrong once (US-011: 74 files had deletions, and one was a real `SEARCH($10, Sarg[[30..40]])` -> `<($10, 40)` plan change). The check: `git diff -U0 -- <goldens> | grep '^-' | grep -v '^---'` must contain only lines that are re-added identically modulo an appended trailing comma or an added end-of-file newline, and every changed `.json` golden must PARSE to an object equal to HEAD's minus exactly the intended new keys. Any other deletion is a regression until proven otherwise.
- New explain fields are backward-compatible FOR FREE: `YamlFormatter` sets `JsonInclude.Include.NON_NULL` (`core/.../utils/YamlFormatter.java:32`) and the JSON path uses Gson, which omits nulls by default and never calls `serializeNulls()`. A field left null is invisible in output, so a staged-only section needs NO explain-mode gate and NO new setting.
- BUT adding a field to `ExplainResponseNodeV2` also requires updating `ExplainResponse.normalizeLf` (`core/.../executor/ExecutionEngine.java:144`): it rebuilds the node through the 3-arg constructor, so any field not explicitly re-set there is silently DROPPED. Same defect family as the Writeable round-trip checklist.
- A test that asserts a POSTURE must not live in a class that a `Staged*IT` subclasses, or the subclass inherits it under the opposite posture and fails. Put both directions in a standalone `PPLIntegTestCase` subclass with an `@After` restoring the settings to null. Precedent: `CalciteStageSplitExplainIT`. Assert on the YAML KEY (`"combine:"`), never the bare word.

- A ZERO-DELETION GOLDEN ADDITION IS A BEHAVIOUR CHANGE, NOT AN ADDITIVE RE-BASELINE, and the additions-only gate above passes it by construction. A golden that gains `shardFragment`/`combine`/`coordinatorTree` sections with NO deletions is a query that was NOT staged before and IS staged now. Check it PER FILE: `git diff -U0 -- <file> | grep -c '^-[^-]'`, and justify every file where that count is 0, individually. This is what exposed US-012's union mis-staging after the implementer's own audit had passed the whole re-baseline as legitimate.
- EXPLAIN COVERAGE DESCRIBES A SPLIT DECISION, IT CANNOT VALIDATE ONE. `StagedCalciteExplainIT` was 266/0 with a live `CalciteLogicalIndexScan` wrongly left in `coordinatorTree`, because explain does not execute. Any story that changes WHICH shapes get staged must add an EXECUTION IT for the affected shape; a new golden is not acceptance evidence. US-012's new `StagedCalcitePPLJoinIT` failed 2 of 43 immediately and produced a second real fix.

## An optimizer pass before the split turns the plan into a DAG (US-012)
- `HepPlanner` INTERNS structurally identical subtrees into a SINGLE SHARED RelNode instance. Adding any HEP/Volcano pass ahead of `StagePlanner.split()` therefore converts the tree into a DAG, and every identity-based assumption in `StagePlanner` must be re-audited. The "use IDENTITY maps for RelNode keys" rule recorded above is still correct but was written for a tree and is NOT sufficient for a DAG: a two-scan UNION over one index collapses to ONE scan instance, so the "more than one `AbstractCalciteIndexScan` means coordinator-only" guard counts 1 and wrongly stages the plan.
- Two layers now defend this, both load-bearing. (1) A targeted shared-subtree guard: refuse to stage when the cut node has MORE THAN ONE PARENT and that parent is a `LogicalJoin`, because a join consumes the shared subtree at two different field-index offsets and replacing both positions with one gathered-rows table conflates independent streams. (2) An unconditional post-split `containsIndexScan(coordinatorTree)` validation that returns the coordinator-only `StagePlan` whenever a live `AbstractCalciteIndexScan` survives on the coordinator. Layer 2 is the general safety net and the one to extend; layer 1 is the specific semantic rule. Sharing along a SINGLE input path (chart/timechart/streamstats) is harmless and still stages, which is why layer 1 is narrow rather than blanket.
- Refusing to stage is NOT a violation of Design Invariant 1 — the plan still runs, entirely on the coordinator. Rejecting or throwing would be the violation.

## When the wire cannot carry something, gather instead of widening the codec (US-012)
- RelJson could not serialize a `SqlTypeName` SYMBOL literal (`cannot serialize enum value to JSON: SqlTypeName.X`, thrown from Calcite's OWN static `RelEnumTypes.fromEnum`). The correct fix was Design Invariant 1 itself: classify a node whose expressions contain a non-round-trippable literal as NEEDS_GATHER, by the same mechanism as the `RexOver` guard. The expression runs on the coordinator, results stay correct, and the codec problem disappears. ASK THIS FIRST, before widening a codec or a wire type.
- Do NOT reach into upstream Calcite statics. An attempt to `sun.misc.Unsafe`-replace the static final `RelEnumTypes.ENUM_BY_NAME` ImmutableMap was rejected in review: process-wide mutation affecting the NON-staged production path and every other Calcite user in the JVM, no happens-before guarantee against concurrent shard-thread reads, and a silent `catch (Exception) { LOG.warn }` degrade. Contrast with US-008's ACCEPTED `operatorTable` reflection, which sets a private field on a freshly created per-deserialize instance and fails loudly — narrowness and loudness are what make that one acceptable.
- AN IN-BAND MAGIC PREFIX IS THE SENTINEL DEFECT SHAPE IN A NEW COSTUME. Encoding special cells as `\u0000BD:<value>` inside the string value is ambiguous with real document data. Use an OUT-OF-BAND discriminator: a tag byte written before each cell (0 = `writeGenericValue`, 1 = BigDecimal as `toPlainString()`, rebuilt with `new BigDecimal(String)`). A tag byte cannot collide with user data. It widens the wire, so the full symmetric checklist applies.

## Aggregate splitting: what actually fixes what (US-012)
- `CoreRules.AGGREGATE_REDUCE_FUNCTIONS` must run BEFORE the split, applied inside `splitIfStaged` on the incoming rel, with the transformed rel DISCARDED when `staged()` is false so the non-staged path and the explain `logical`/`physical` sections stay bit-identical. It is what makes stddev/var work, NOT the split rule: Calcite 1.42's `DEFAULT_FUNCTIONS_TO_REDUCE` is `SqlKind.AVG_AGG_FUNCTIONS` + `COVAR_AVG_AGG_FUNCTIONS` + `SUM` and `canReduce()` dispatches on `SqlKind`, so it matches PPL's custom `NullableSqlAvgAggFunction` (`PPLBuiltinOperators.java:484-492`). Those failures were unreduced avg-family functions with no enumerable implementor, never a splittability problem.
- The partial aggregate is the ORIGINAL Aggregate node UNCHANGED — for COUNT/SUM/SUM0/MIN/MAX the partial accumulator state IS the value — so no new RelNode and no plan reconstruction is needed. Only the coordinator-side MERGE mapping differs: COUNT->SUM, SUM->SUM, SUM0->SUM0, MIN->MIN, MAX->MAX.
- The exclusions matter more than the inclusions. `isDistinct()` MUST refuse (per-shard COUNT DISTINCT summed is wrong) and multiple `groupSets` MUST refuse (rows from different grouping sets cannot be merged on group keys alone). `filterArg >= 0` is safe precisely BECAUSE the shard-local partial is the identical node, filter included.
- Promoting the cut to the Aggregate is what keeps finalization correct: everything ABOVE the Aggregate — including the AVG division `Project` that `AGGREGATE_REDUCE_FUNCTIONS` produces — stays in `coordinatorTree` by construction. A per-shard division would be silently wrong. No tri-state placement is needed; `Aggregate` stays NEEDS_GATHER in the placement floor and the promotion is a post-placement rewrite.
- PROVE ASSOCIATIVITY BY REDUCING THE SAME INPUT IN TWO DIFFERENT BATCH GROUPINGS and asserting identical output. `reduce()` runs in batches of 512 and its output is fed back in, so a single-batch test proves nothing about the property that matters.

## OpenSearch aggregation lifecycle constraints
- `InternalAggregation.reduce()` is called in batches of `batched_reduce_size` (default 512) by `QueryPhaseResultConsumer.PendingReduces`. It MUST be associative. There is no opt-out.
- `mustReduceOnSingleInternalAgg()` only forces reduce() when a single shard returned; it does NOT disable batching.
- Therefore the wire type must carry UNFINALIZED accumulator state (avg ships {sum, count}, never an average).
- Batched reduce lowers peak memory only when the combine reduces volume. CONCAT gains nothing.
- `Aggregator.collect()` can read _source via `SearchContext.lookup().getLeafSearchLookup(ctx).source()`, and this works under `size: 0` because it is independent of the fetch phase.
- `size: 0` sets `hasTopDocs=false`, skipping the fetch phase, so no reader context and no PIT is created.
- `CollectionTerminatedException` terminates the CURRENT LEAF ONLY — it is caught by `ContextIndexSearcher#searchLeaf()` and the leaf loop continues. Stopping a whole shard needs a shard-global counter plus a guard in `getLeafCollector()`.
- `allow_partial_search_results` defaults to TRUE. Every request this PoC builds must set `allowPartialSearchResults(false)`, or a budget breach returns HTTP 200 with partial results.
- Transport ceiling from data node to coordinator is 30% of JVM heap, hardcoded in `TcpTransport`. There is no `transport.max_message_size` setting.

## A PROMOTION PATH MUST RE-APPLY EVERY GUARD THE DEFAULT PATH APPLIES (US-013)
- `StagePlanner.split()` now has THREE exit paths: `trySplitAggregate` (MERGE_AGG), `trySplitLimit` (LIMIT), and the default CONCAT path. Each promotion returns EARLY, so it BYPASSES every guard that lives further down `split()`. US-013 shipped `trySplitLimit` missing the relevance-function guard, and the audit then found `trySplitAggregate` missing it too — the same omission twice, in code written a story apart. Whenever a new guard is added to the CONCAT path, it MUST be added to every promotion path, and whenever a promotion path is added it must re-apply the full guard set. A promotion returns `null` (fall through to CONCAT, which owns the single `coordinatorOnly` decision site) rather than returning `coordinatorOnly` itself.
- THE GUARD MUST BE APPLIED TO THE PROMOTED CUT, NOT THE ORIGINAL CUT. Both promotions initially guarded `cutNode` while replacing the PROMOTED node (`sortNode`/`agg`) with the gathered-rows table. A shared promoted node has exactly ONE child-side parent, so `isSharedNode(cutNode)` is false and the guard could never fire; `replaceSubtree` then collapses both join inputs into one gathered-rows scan, and the `containsIndexScan` backstop does NOT catch it because no live scan survives. Guard whatever node `replaceSubtree` is about to replace.
- `isSharedNode` counts reference SITES (edges), not distinct parents, which is the correct semantics here: a `LogicalJoin` with both inputs pointing at one interned instance gives count 2.

## Rule 4: unordered limit pushdown, and the two decisions inside it (US-013)
- The promotion fires when the node directly above the cut is a `Sort` with EMPTY collation, a non-null `RexLiteral` fetch >= 0, and offset null-or-zero. Ordered `Sort`+`Fetch` is deliberately left to US-014's TOP_N — the empty-collation test is the whole boundary between the two rules. A non-zero offset is refused because per-shard `Fetch(N)` with a coordinator offset is wrong; refusing costs only the optimization, since the plan still stages via CONCAT.
- SHIP A STANDARD `LogicalSort` INTO THE FRAGMENT, NEVER `LogicalSystemLimit`. The plan-level `LogicalSystemLimit(QUERY_SIZE_LIMIT)` wrapping EVERY plan is itself an unordered fetch and IS promoted, but it is a custom RelNode class and Design Invariant 5 requires standard operators on the wire. `LogicalSort.create(input, RelCollations.EMPTY, null, fetch)` round-trips through `RelFragmentCodec` and reaches `EnumerableLimit` with no new optimizer rule — verified, not assumed.
- Because the system limit is promoted, this story migrated 66 of 114 staged goldens from `CONCAT` to `LIMIT{n:10000}`. When a query has its own `head N`, the INNERMOST unordered fetch is promoted (`LIMIT{n:5}`) and the outer limits stay in `coordinatorTree` — promotion is single-step and does NOT cascade.
- PUSHING THE LIMIT AND TERMINATING DOC COLLECTION ARE TWO SEPARATE DECISIONS WITH DIFFERENT PRECONDITIONS, and conflating them is the correctness trap in this rule. Pushing `Fetch(N)` shard-local is correct even with a shard-local `Filter` below it (the fragment's own Fetch truncates). Terminating LUCENE DOC COLLECTION at N buffered rows is NOT, because the aggregator buffers scan rows and runs the fragment afterwards: with a Filter in the fragment, stopping at N buffered rows can yield FEWER than N output rows while more matching docs existed — a silent truncation and a Design Invariant 3 violation. So `earlyTerminationLimit` is a SEPARATE nullable field, set only when every node between the promoted Sort and the scan is cardinality-preserving (Project with no `RexOver`, or Calc with no `RexOver` and no condition). Nested expansion pushing the buffer slightly PAST the limit is harmless — the fragment's Fetch truncates.
- Early termination needs BOTH throw sites the design doc names: `CollectionTerminatedException` from `collect()` AND a `terminated`-flag guard at the top of `getLeafCollector()`. The exception alone is caught per-leaf by `ContextIndexSearcher#searchLeaf()` and the leaf loop continues. Check early termination BEFORE the US-009 row-budget check — a legitimately bounded query must never fail the safety budget — and flush the pending circuit-breaker byte batch on this exit path exactly as the budget throw does.
- `LIMIT` reduce is concatenate-then-truncate-at-n and is associative because truncation never adds rows. Copy the truncated list (`new ArrayList<>(sub)`); returning a `subList` VIEW pins the whole untruncated backing buffer on the coordinator.

## Relevance functions can NEVER run on the shard fragment or the coordinator tree (US-013)
- Every relevance function (`query_string`, `match`, `match_phrase`, `match_bool_prefix`, `match_phrase_prefix`, `simple_query_string`, `multi_match`, `query`, `wildcard_query` — all nine built from the one `RelevanceQueryFunction` singleton at `PPLBuiltinOperators.java:432-450`) has a `NotNullImplementor` that UNCONDITIONALLY throws `UnsupportedOperationException: Relevance search query functions are only supported when they are pushed down` (`RelevanceQueryFunction.java:97`). They exist for plan construction only; evaluation is delegated to the OpenSearch query DSL. No optimizer rule can make them computable in Janino, so the correct response is a STAGING REFUSAL (Design Invariant 1 — the plan still runs, entirely on the coordinator), never a codec or rule-set workaround.
- Guard in two layers: the placement floor classifies a Project/Filter/Calc containing such a call as NEEDS_GATHER, and a post-split check returns `coordinatorOnly` when the coordinatorTree still contains one (reachable because the floor only inspects Project/Filter/Calc, not e.g. an Aggregate `filterArg` or a Join condition). Known gap, judged unreachable and left with a note: the `RexVisitorImpl` does not descend into `RexSubQuery`.
- CALCITE HIDES THE REAL CAUSE OF A FRAGMENT COMPILATION FAILURE. `EnumerableRelImplementor.implementRoot` catches the underlying `RuntimeException` and rethrows `IllegalStateException("Unable to implement " + plan)` with the original attached as a SUPPRESSED exception — and the REST error body drops suppressed exceptions entirely. An "Unable to implement X" message from a shard is therefore never the diagnosis, only the symptom. Reproduce it in a unit test through the package-private `CalciteExecAggregator.executeFragment` (which takes a literal `List<Object[]>` and needs no cluster) and print `getSuppressed()`. That turned a whole round of "query_string UDF incompatibility" hand-waving into a one-line root cause, and left a permanent regression test behind.
- UNEXPLAINED, recorded rather than guessed: at HEAD the staged explain goldens showed `LogicalFilter(query_string(...))` INSIDE `shardFragment` with `combine: CONCAT`, yet `StagedCalciteWhereCommandIT.testWhereEquivalentSortCommand` PASSED at HEAD (proven by stashing and re-running the single test). Per the root cause above that fragment could not have compiled, so execute and explain must have been splitting different rels for this shape. The mechanism by which US-013 caused the relevance call to actually reach shard compilation was NOT determined. The guard is justified independently by the unit-test-proven root cause, and it now makes explain and execute agree — both refuse.

## Re-baselining goldens: regenerate mechanically, never by hand
- HAND-AUTHORING GOLDEN CONTENT FROM AN EXPECTATION OF WHAT THE PLAN SHOULD BE IS A DEFECT GENERATOR. US-013's first re-baseline attempt wrote a `bank` `avg(balance)` MERGE_AGG plan into `chart_use_other.yaml`, which had held an `otel_logs` JOIN/CONCAT plan (pure cross-contamination), and hand-wrote two limit goldens asserting `LIMIT{n:10000}` where the code correctly produced `LIMIT{n:5}`. The whole ~110-file re-baseline had to be thrown away with `git checkout HEAD -- expectedOutput/` and redone.
- THE MECHANICAL METHOD: derive the test-method -> golden-filename mapping from the TEST SOURCE (the literal argument to `loadExpectedPlan("<name>.yaml")` in the method body), never from the test's NAME; parse each `<failure>` in the JUnit XML and write the ACTUAL document to the golden that THAT test loads; refuse to write when the filename cannot be resolved unambiguously and list those for manual handling. Converging multi-golden tests took 5 regenerate-and-rerun cycles. Every byte must come from a real test run.
- FOUR GATES, now including a new one. (i) `git diff -- expectedOutput/calcite/` MUST be empty. (ii) LOGICAL/PHYSICAL IMMUTABILITY PER FILE: extract the `logical:` and `physical:` blocks from `git show HEAD:<path>` and from the working tree and diff them for EVERY changed file — this is the gate that catches cross-contamination, and it is stronger than the additions-only gate. (iii) per-file zero-deletion check, justified individually. (iv) NEW — SECTION-LOSS CHECK: list every golden that loses its `shardFragment:`/`combine:`/`coordinatorTree:` sections entirely and explain each one; a file becoming non-staged is a coverage reduction that must have a named cause.
- BUILD THE COMBINE-MODE TRANSITION MATRIX YOURSELF AND MAKE IT BALANCE. Two subagent censuses of the same tree disagreed with each other and neither balanced (-70 CONCAT against +75 elsewhere). A 20-line script reading the `combine:` line from `git show HEAD:<file>` and from the working tree gave the exact truth: 66 CONCAT->LIMIT, 5 CONCAT->none, 1 MERGE_AGG->CONCAT, 1 new file. Every unexpected transition was then explainable by name. Grep-and-count censuses of golden directories are not trustworthy; a per-file transition matrix is.
- A CHECKSUM OVER `find`-RELATIVE PATHS DEPENDS ON THE WORKING DIRECTORY. A no-drift proof of the form `find ... | sort | xargs md5sum | md5sum` must be run from the same directory both times, or it reports a false difference and a subagent will invent a reason for it.

## Calcite facts
- Aggregate splitting bottoms out per function: `SqlSplittableAggFunction` with `CountSplitter`, `SumSplitter`, `Sum0Splitter`, `SelfSplitter`. If `unwrap(SqlSplittableAggFunction.class)` returns null the call cannot be split.
- There is no generic mechanism to split Window, Sort, Join, or Distinct. The standard fallback is gather to SINGLETON.
- Limit-pushability is per-operator: exact below Project/Calc, merges with Sort into top-N, exact per-branch for Union ALL. NOT below Filter, Aggregate, general Window, Join, or Union DISTINCT.
- PPL `dedup` already lowers to `ROW_NUMBER() OVER (PARTITION BY ...)` plus a `<= k` filter — no custom operator is involved on the Calcite path.

## Custom logical operators (audit result, US-001)
- Only three custom logical RelNodes exist on the Calcite path:
  - `LogicalSystemLimit` (`core/.../calcite/plan/rel/LogicalSystemLimit.java:25`, a `Sort` subclass, present in every plan)
  - `LogicalDedup` (`core/.../calcite/plan/rel/LogicalDedup.java:20`, transient during HEP, lowered by `PPLDedupConvertRule`)
  - `LogicalGraphLookup` (`core/.../calcite/plan/rel/LogicalGraphLookup.java:22`, irreducible, from `graphLookup`, becomes `CalciteEnumerableGraphLookup`)
- `TimeWindow` (`core/.../calcite/plan/TimeWindow.java:15`) is dead code never instantiated.
- Every other PPL command produces only standard Calcite operators.
- `dedup` uses `ROW_NUMBER` exclusively (never `RANK`/`DENSE_RANK`) via `CalciteRelNodeVisitor.visitDedupe()` (line 2208) and `PPLDedupConvertRule.buildDedupNotNull()`/`buildDedupOrNull()`.
- `dedup consecutive=true` throws `CalciteUnsupportedException` (`CalciteRelNodeVisitor.java:2217`).

## Staged execution wiring (US-008, COMPLETE)
- Hook: `OpenSearchExecutionEngine.execute(RelNode, CalcitePlanContext, ResponseListener)` in `opensearch`. NOT `core/QueryService` — `core` cannot see `opensearch`.
- Gate: `StagePlan.staged() && plugins.calcite.pushdown.enabled == false`, read via `stagePlan.shardScan().getOsIndex().getSettings()`. No new setting. When pushdown is enabled (the production default) nothing changes.
- Gathered-rows row type is `stagePlan.shardFragment().getRowType()`, NEVER `shardScan().getRowType()`. They differ whenever a shard-local Project/Filter sits above the scan, and using the scan's type silently reads wrong column indices.
- `OpenSearchClient.search(OpenSearchRequest)` parses the raw `InternalAggregation` into `ExprValue` iterators and so CANNOT return the real `InternalCalciteExec`. Use `client.getNodeClient().get().search(searchRequest).actionGet()`. Staged execution is therefore NodeClient-only.
- `allowPartialSearchResults` is on `SearchRequest`, NOT `SearchSourceBuilder` (invariant 7).
- Tier 2 is `CoordinatorTreeExecutor` — same HEP + Volcano + `toBindable` + custom `DataContext` recipe as the shard side, wrapped in `CalciteClassLoaderHelper.withCalciteClassLoader`. It needs the FULL enumerable rule set, not just `ENUMERABLE_TABLE_SCAN_RULE`, because `LogicalSystemLimit` (a `Sort`) lands on the coordinator as a logical node.
- STILL OPEN (deliberately, none of them blocking): `buildStagedSearchRequest` is public static only so a test in another package can reach it; the coordinator `DataContext` returns null for `UTC_TIMESTAMP`; the `OpenSearchRestClient` path throws `IllegalStateException("Staged execution requires a NodeClient")`; `CoordinatorTreeExecutor.execute`'s `gatheredRowType` parameter is redundant because the coordinatorTree's leaf already carries its row type.

## The staged response must derive ExprType from the plan, not from the Java value
- The staged row-conversion loop originally called the single-arg `ExprValueUtils.fromObjectValue(Object)`, which dispatches on the RUNTIME CLASS. Shard rows carry temporal values as epoch-millis `Long`, so a date came back as `1420070400000` while the JDBC path returns `"2015-01-01 00:00:00"`. Dispatching on the runtime class can never be right here: the wire representation is lossy about intent.
- Fix pattern, reusable for any future staged output type: pre-compute `ExprType[]` ONCE from `coordinatorTree.getRowType()` outside the row loop via `OpenSearchTypeFactory.convertRelDataTypeToExprType`, pass it to the two-arg `fromObjectValue(Object, ExprType)`, and have the schema-building loop reuse the SAME array. Values and declared schema then cannot diverge by construction.
- `ExprValueUtils.fromObjectValue(Object, ExprType)` lives in `core` and is shared. It already converts `Long` -> TIMESTAMP/DATE/TIME via `Instant.ofEpochMilli`; it now also returns `LITERAL_NULL` for a null input instead of NPE-ing.
- Any staged query projecting a temporal column exercises this. Assert against the JDBC path's exact string form, including the sub-second-nanos variant (`"1970-01-19 08:31:22.955"`), not just whole seconds — the formatter branches on `getNano() == 0`.

## Nested fields on the staged shard path: expand with sibling alignment
- OpenSearch `nested` sub-documents are SEPARATE HIDDEN LUCENE DOCUMENTS. The parent has no doc_values for a nested leaf, and `_source` extraction of `address.city` on the parent returns a FLATTENED List of every sub-document's value. A Calcite filter comparing that List to a scalar is always false — 0 rows, no error. This is the single most dangerous shape on this path because it is silent.
- The wire `FieldDescriptor` type for `address.city` is the LEAF type (`text`), NOT `nested`, so type-based dispatch alone can never detect the situation. Detection must come from the MAPPING.
- Nested paths are resolved on the SHARD, not shipped: `CalciteExecAggregator.findNestedPath` walks the dotted path from the leaf upward asking `SearchContext.getQueryShardContext().getObjectMapper(parent)` whether it is nested; the FIRST hit walking upward is the innermost path. This deliberately avoids touching the wire format — prefer shard-side mapping resolution over widening `FieldDescriptor`, because asymmetric Writeable round-trip is this codebase's most invisible defect class.
- `ShardRowReader.readRows(doc)` returns `List<Object[]>`: one output row per nested sub-document. Any field with a non-null nested path is read from `_source` (never doc_values). `readRow(doc)` is unchanged and still serves the non-nested case, so non-nested queries are byte-for-byte unaffected.
- SIBLING ALIGNMENT IS THE LOAD-BEARING PROPERTY: group requested fields BY nested path, expand each distinct path's sub-document array ONCE, and read all fields of that path from the SAME sub-document. Expanding per FIELD independently would cross-product siblings and be silently wrong. A test for this must use MULTIPLE sub-documents and assert the pairing — with one sub-document, a correct implementation and a cross-producting one are indistinguishable.
- Fields under DIFFERENT nested paths DO cross-product. Documented in a code comment and in the story notes; not silent.
- Absent vs malformed must be separated: a nested array genuinely MISSING from `_source` is a legitimately sparse parent and yields one row with null nested values (correct — a downstream filter drops it). A value PRESENT with an unexpected shape THROWS, naming the nested path, the field, and the actual runtime class. Collapsing both into "return nulls" reintroduces the silent-zero-row bug being fixed.
- Row cardinality now exceeds document count for nested queries, so `rowsCollected` counts POST-expansion buffered rows. US-009's row budget must be written with that in mind.

## Prove a "pre-existing failure" by stashing, do not assert it
- A parent IT that fails both before and after a change is only credible if you SHOW it: `git stash push`, re-run the single test, read the XML, `git stash pop`. `CalciteWhereCommandIT.testScriptFilterOnDifferentNestedHierarchyShouldThrow` was verified this way. Cheap, and it removes the most common way a real regression gets waved through — especially when the change touches shared `core` code that could alter an exception type the test asserts on.


## Separating staged-path defects from posture limitations
- When a staged IT fails, do NOT reason about whether the cause is staging or `pushdown.enabled=false`. Neutralize ONLY the gate (`if (false && ...)`) and re-run the same IT classes — they set the settings themselves, so the run isolates the posture. This one experiment invalidated a whole round of plausible-but-wrong gap analysis in US-008.

## Integration tests share ONE cluster
- `integTest` runs every IT class against a single cluster, so a transient cluster setting applied in `init()` leaks into every class that runs afterwards, in non-deterministic order. Always restore to `null` in teardown. Precedent: `integ-test/.../remote/CalcitePPLAggregationPaginatingIT.java:18-22`.

## Delegating code review
- `reviewer` missed one real defect per round in US-003/005/007 while catching only style items, then caught BOTH criticals in US-008. The difference was the prompt: name the project's historical defect shapes explicitly (sentinel/placeholder bypass, silent catch-and-degrade fallback, test whose NAME does not match what its BODY constructs, comment asserting an unenforced rule) and require a hunted-each-one checklist in the output. Do this every round.

## Design invariants — do not violate
1. The split must be TOTAL over RelNode. Absence of an optimization rule means the operator runs on the coordinator. Never reject a plan.
2. Never emit a Painless script query. If a predicate is not index-accelerable, leave it as a residual Filter in the fragment.
3. Never silently truncate. Either the limit is provably pushable, or the budget refuses the query with a diagnosable error.
4. One search request per OpenSearchIndexScan. Never create a PIT, scroll, or search_after on this path.
5. Standard Calcite operators only.

Full design: `docs/dev/poc-staged-calcite-exec-design.md`

## The stage split: StagePlanner (US-007)
- `opensearch/src/main/java/org/opensearch/sql/opensearch/stage/StagePlanner.java` — `static StagePlan split(RelNode root)`. Never throws, never returns null, for any RelNode tree.
- MODULE DEVIATION, and it is permanent: the design doc assigns StagePlanner to `core`, but `core/build.gradle` has NO dependency on `:opensearch` while StagePlanner must reference `CombineDescriptor`, `RelFragmentCodec`, and `AbstractCalciteIndexScan` — all in `opensearch`. It therefore lives in `opensearch`. Dependency direction is `opensearch --api--> core`, one way only. Any future story that the doc places in `core` but which touches the stage package has the same problem.
- Shard-scan recognition is the single package-private predicate `StagePlanner.isShardScan(RelNode)` → `node instanceof AbstractCalciteIndexScan`. Widen THERE, nowhere else. Do NOT make every `TableScan` SHARD_LOCAL — that would falsely claim non-OpenSearch tables are shard-distributed.
- Placement is one memoized bottom-up pass into an `IdentityHashMap<RelNode, Boolean>`, then a top-down walk reading the memo to find the highest SHARD_LOCAL node. Use IDENTITY maps for RelNode keys throughout — `AbstractRelNode` does not override `equals`/`hashCode`, so `equals` is reference equality today, but relying on that implicitly is fragile.
- A `Project` or `Calc` containing a `RexOver` is NEEDS_GATHER, not SHARD_LOCAL. PPL lowers window functions (`dedup`, `eventstats`) into a `LogicalProject` holding `ROW_NUMBER() OVER (...)`, and per-shard numbering restarts at 1, so shipping it shard-local and CONCAT-ing is SILENTLY WRONG. Guards: `RexOver.containsOver(project.getProjects(), null)` and `RexOver.containsOver(calc.getProgram())`. A `Filter` needs no such guard — the Calcite 1.42.0 validator rejects a `RexOver` in a filter condition. Partial window evaluation is US-015's `RANK_LIMIT` rule and is the ONLY correct way to make windows shard-local.
- The shardFragment's leaf is NOT the `AbstractCalciteIndexScan`. `split()` replaces it with a plain `LogicalTableScan` over `[RelFragmentCodec.SCHEMA_NAME, <indexName>]` carrying the SAME row type, so `RelFragmentCodec.serialize(shardFragment)` round-trips. The original scan is preserved on `StagePlan.shardScan()` so a later story can read index name, pushed-down DSL, and field list without re-walking the tree.
- The coordinatorTree replaces the whole cut subtree with a gathered-rows `LogicalTableScan` whose row type is the CUT NODE's row type, backed by `RelFragmentCodec.ShardRowSourceTable` parameterized with `StagePlanner.GATHERED_ROWS_STASH_KEY` = `"calcite_exec.gathered_rows"` (table name `_gathered_rows`). `ShardRowSourceTable` now has a 2-arg ctor taking a stash key; the 1-arg ctor still defaults to `SHARD_ROWS_STASH_KEY`, so the US-005 shard path is untouched.
- ZERO or MORE THAN ONE `AbstractCalciteIndexScan` (e.g. a join across two indices) has no single gather boundary, so `split()` returns a coordinator-only `StagePlan`: `staged()==false`, `coordinatorTree()==root` untouched, `shardFragment()`/`shardScan()`/`combine()` null. This preserves Design Invariant 1 (never reject a plan). Multi-scan staging is deliberately out of PoC scope. Callers MUST check `staged()`.
- `LogicalSystemLimit` is a `Sort` subclass, so the generic floor makes it NEEDS_GATHER and it lands on the coordinator. That is correct for the floor; US-013/US-014 own limit pushdown. Do not special-case it.
- Tree rebuilds use `node.copy(node.getTraitSet(), newInputs)`. Safe for `LogicalSystemLimit`, Project, Filter, Calc because the replacement leaf's row type is identical to the original's, so no `RexInputRef` shifts index or type. Preserve row type exactly whenever swapping a leaf.

## Custom aggregation: calcite_exec (US-002)
- Aggregation type name: `calcite_exec`
- Package: `org.opensearch.sql.opensearch.stage` (in `opensearch` module)
- Classes:
  - `CombineDescriptor` — enum of reduce modes (CONCAT, MERGE_AGG, LIMIT, TOP_N, RANK_LIMIT) plus parameters
  - `CalciteExecAggregationBuilder` — XContent parser + Writeable builder; fields: plan, fields, combine, rowBudget
  - `CalciteExecAggregatorFactory` — creates aggregator via `createInternal(SearchContext, Aggregator, CardinalityUpperBound, Map<String,Object>)`
  - `CalciteExecAggregator` — extends MetricsAggregator; collects docs, executes fragment, emits InternalCalciteExec
  - `InternalCalciteExec` — InternalAggregation; carries rows + combine descriptor; reduce() applies combine mode
- Registration: `SQLPlugin.getAggregations()` (SQLPlugin now implements SearchPlugin)
- Module-visibility rule: `opensearch` module has the full opensearch server jar (`opensearch/build.gradle:36`); `core` has only `opensearch-core`. Any class touching InternalAggregation, AggregatorFactory, MetricsAggregator, or SearchContext must live in `opensearch` (or `plugin`), never `core`.
- CombineDescriptor modes: CONCAT (US-002), MERGE_AGG (US-012), LIMIT (US-013), TOP_N (US-014), RANK_LIMIT (US-015)

## Fragment codec: RelFragmentCodec (US-003)
- `opensearch/src/main/java/org/opensearch/sql/opensearch/stage/RelFragmentCodec.java` — `serialize(RelNode) -> base64 RelJson` and `deserialize(base64, indexName, List<FieldDescriptor>) -> RelNode`.
- Calcite 1.42.0 signatures that make custom RelJson injection possible: `RelJsonWriter(JsonBuilder, UnaryOperator<RelJson>)` and `RelJsonReader(RelOptCluster, RelOptSchema, Schema, UnaryOperator<RelJson>)`. Use these to inject `ExtendedRelJson` so PPL operators round-trip. Plain `RelJson` would silently lose them.
- `RelJsonSerializer.getPplSqlOperatorTable()` is now `public static` (backing field is `volatile`, so the double-checked-locking singleton is correct). ALWAYS reuse it — never re-chain PPLBuiltinOperators + SqlStdOperatorTable + OperatorTable + SqlLibrary by hand.
- `ExtendedRelJson.create(jsonBuilder)` leaves `inputTranslator = null`, and `withOperatorTable()` NPEs on a null translator because the 3-arg ctor `requireNonNull`s it. So on the read path you MUST chain `.withInputTranslator(...)` before `.withOperatorTable(...)`. The translator itself is never invoked — `RelJsonReader` resolves input refs through its own `RelInput` — so it should throw `UnsupportedOperationException` rather than fabricate refs. An earlier draft fabricated `SqlTypeName.ANY` refs, which would have been silently wrong if ever reached.
- Table path convention is `[OpenSearch, <indexName>]` (`RelFragmentCodec.SCHEMA_NAME`). The SAME path must be registered on both the serialization and the deserialization side or `RelOptUtil.toString()` will not match.
- `RelFragmentCodec.SHARD_ROWS_STASH_KEY` = `"calcite_exec.shard_rows"`. `ShardRowSourceTable` is a `ScannableTable` that reads `List<Object[]>` from `DataContext.get(SHARD_ROWS_STASH_KEY)` and returns an empty enumerable when absent. US-005 injects rows here.

## Wire type strings are OPENSEARCH type names, not SqlTypeName names
- `CalciteExecAggregationBuilder.FieldDescriptor.type` is a free-form `String` carrying an OpenSearch field type. The authoritative example at `docs/dev/poc-staged-calcite-exec-design.md:270-272` is `{"name":"account_number","type":"long"}` / `{"name":"gender","type":"keyword"}`.
- Therefore `SqlTypeName.valueOf(fd.getType())` ALWAYS throws on real wire data. `RelFragmentCodec` owns the mapping: keyword/text→VARCHAR, long→BIGINT, integer→INTEGER, double→DOUBLE, float→REAL, boolean→BOOLEAN, date→TIMESTAMP; anything else throws naming the field and the type. Extend that map when a story needs a new type — do not add a second mapping elsewhere.
- Do NOT reuse `OpenSearchTypeFactory.convertExprTypeToRelDataType` for this: it takes an `ExprType` object rather than a string, and returns UDT wrapper types (ExprDateType, ExprTimeStampType, …) for date/time/timestamp/ip that do not survive the RelJson round-trip.
- Lesson: write unit tests against the REAL wire spellings from the design doc. The first draft's tests fed `"BIGINT"`/`"VARCHAR"` and passed green while the production path was broken for every actual caller.

## Shard row materialization: ShardRowReader (US-004)
- `opensearch/src/main/java/org/opensearch/sql/opensearch/stage/ShardRowReader.java` owns ALL field-value extraction for the shard fragment. One `FieldReader` closure per requested field, built once per Lucene leaf in `CalciteExecAggregator.getLeafCollector()`; `readRow(doc)` returns an `Object[]` with exactly one slot per requested field, in request order, `null` when the field is absent from a doc.
- Type dispatch keys off the SAME OpenSearch type strings as the wire (`keyword`, `long`, `integer`, `double`, `float`, `boolean`, `date`, `text`) — see the wire-type note above. Keep this switch and `RelFragmentCodec`'s SqlTypeName map in sync: adding a type needs BOTH.
- doc_values access uses `advanceExact(doc)`, never `advance()`. `advanceExact` is stateful per reader instance, so a reader MUST be created per leaf — never cache a `FieldReader` across `getLeafCollector()` calls or docIDs from a later leaf will silently miss.
- Encoding decisions in the Object[]: keyword → `String` (BytesRef.utf8ToString), long/date → `Long` (date is epoch millis), integer → `Integer`, double → `Double` via `NumericUtils.sortableLongToDouble`, float → `Float` via `sortableIntToFloat`, boolean → `Boolean` from 0/1. Numeric doc_values are stored sortable-encoded — reading the raw long for a double/float gives garbage.
- `text` (and any field with no doc_values) falls back to `_source`. `ShardRowReader.create()` does NOT position the `SourceLookup`; the CALLER must call `sourceLookup.setSegmentAndDocument(ctx, doc)` before `readRow(doc)`. Obtain the lookup via `SearchContext.lookup().getLeafSearchLookup(ctx).source()` — this works under `size: 0` because it is independent of the fetch phase.
- `InternalCalciteExec` carries `rowsCollected` and `rowsEmitted` as VLongs (both in `writeTo`/StreamInput ctor/XContent/equals/hashCode). They are currently always equal; they diverge only once US-009 enforces the row budget.

## Shard fragment execution: the compile-and-run pipeline (US-005)
- `CalciteExecAggregator.buildAggregation()` is the single execution entry point on the shard. One code path only: `RelFragmentCodec.deserialize` -> HEP pass -> Volcano pass -> Janino `Bindable` -> `bind(DataContext)` -> drain. There is deliberately NO bypass, no sentinel plan value, and no catch-and-return-raw-rows fallback. A bad plan MUST fail loudly. Do not reintroduce one to keep an older test green — fix the test instead.
- Reaching a `Bindable` needs TWO optimizer passes, not one:
  1. HEP: `PROJECT_TO_LOGICAL_PROJECT_AND_WINDOW`, `FILTER_TO_CALC`, `PROJECT_TO_CALC`, `CALC_MERGE`.
  2. Volcano: convert to `EnumerableConvention`, then `EnumerableInterpretable.toBindable(ImmutableMap.of(), null, rel, Prefer.ARRAY)`.
  Why the HEP pass is mandatory: `EnumerableProject.implement()` throws `UnsupportedOperationException` under `Prefer.ARRAY`, so Projects must become Calcs; and a `RexOver` sitting inside a `LogicalProject` NEVER becomes an `EnumerableWindow` unless `ProjectToWindowRule` extracts it first. A single Volcano pass silently fails on both.
- The `SparkHandler` argument to `toBindable` is `@Nullable` and `null` is the CORRECT value — that is precisely the branch that Janino-compiles. Passing a handler would route to Spark.
- `CalciteClassLoaderHelper.withCalciteClassLoader(Callable, callerClass)` (in `core`, visible from `opensearch`) MUST wrap the whole compile+bind+drain block. Janino resolves classes through `Thread.currentThread().getContextClassLoader()` (CALCITE-3745); without the wrapper the generated code cannot see plugin classes on a data node. The helper restores the loader in a `finally`.
- `DataContexts.of(Map)` is NOT usable here: generated `EnumerableTableScan` code calls `root.getRootSchema().getSubSchema("OpenSearch").getTable(...)` at runtime and `DataContexts.of` leaves `rootSchema` null. Use a custom `DataContext` serving BOTH the root schema AND the `SHARD_ROWS_STASH_KEY` slot. It currently returns null for `DataContext.Variable.UTC_TIMESTAMP` — a fragment containing `NOW()`/`CURRENT_TIMESTAMP` will NPE in `UserDefinedFunctionUtils.restoreFunctionProperties:168`. Whichever story first ships a temporal fragment must fix that, and must verify the unit (millis vs nanos) against Calcite 1.42 rather than guessing.
- `Prefer.ARRAY` returns a BARE SCALAR, not an `Object[]`, when the output row type has exactly one field. Any drain loop needs that guard or single-column fragments blow up on the cast.
- The row buffer is `List<Object[]>` (matching `ShardRowReader.readRow` and the stash contract), never `List<List<Object>>`.
- `RelFragmentCodec`'s deserialization planner registers `ConventionTraitDef.INSTANCE` and `RelCollationTraitDef.INSTANCE`. Both are required for the EnumerableConvention conversion; a cluster without them cannot be optimized at all.
- `executeFragment(...)` is package-private static precisely so unit tests can drive compile-and-run with a literal `List<Object[]>` and no aggregation framework. Prefer that over an IT when testing plan shapes.
- Do NOT route shard execution through a JDBC `Connection`/`RelRunner` (`CalciteToolsHelper.OpenSearchRelRunners`). That is the coordinator path; the data node compiles a `Bindable` directly.

## Pushdown and PredicateAnalyzer
- `PredicateAnalyzer` lives at `opensearch/src/main/java/org/opensearch/sql/opensearch/request/PredicateAnalyzer.java` and is a `RexVisitorImpl<QueryBuilder>`. Entry points: `analyze(RexNode)` (returns `QueryBuilder` or throws) and `analyzeExpression(RexNode)` (same, no script fallback).
- The predicate path can NO LONGER emit a Painless script. The script-query emission path (`ScriptQueryExpression` in `Visitor.tryAnalyzeOperand` and the `catch`-and-wrap in `analyzeExpression`) is deleted as of US-006.
- Pushdown refusal is signalled by `PredicateAnalyzerException` or `ExpressionNotAnalyzableException`. This is SAFE because:
  - `FilterIndexScanRule` only calls `call.transformTo()` on a non-null result from `PredicateAnalyzer` — a thrown exception means the Filter stays intact in the Calcite plan.
  - `AggregateIndexScanRule` only calls `call.transformTo()` when `CalciteLogicalIndexScan.pushDownAggregate()` returns non-null; that method catches `PredicateAnalyzerException`, logs at debug, and returns null.
- DANGER: nested-field aggregations REQUIRE pushdown and have no Calcite fallback. If a filter on a nested-field aggregation is refused by `PredicateAnalyzer`, the query fails with HTTP 500 PLANNING_ERROR. Any future narrowing of pushability MUST run `CalciteExplainIT` (all 266 tests) as a regression gate.
- The only remaining `new ScriptQueryExpression` in main is in `AggregateAnalyzer` (~line 187, for aggregation MEASURE scripts) and the sort path (`SortAnalyzer`). Neither is a predicate.
- Explain goldens live under `integ-test/src/test/resources/expectedOutput/calcite/` and are re-baselined by editing the YAML/JSON files directly.

## Row budget and circuit breaker on the shard (US-009)
- Budget breach is a HARD exception: `RowBudgetExceededException extends OpenSearchException`, thrown from `CalciteExecAggregator.collect()` when `rowsCollected > rowBudget` (checked AFTER buffering, so exactly-budget succeeds). Message: `<forcingOperator> requires all rows on one node; gathered N rows, budget M` with `%,d` grouping; subject is the literal `"this query"` when nothing forced a gather.
- The design doc's OTHER throw site — `CollectionTerminatedException` + a `getLeafCollector()` guard — is ONLY for an exactly-pushable limit (US-013 rule 4). Never use it for the budget: it is caught per-leaf by `ContextIndexSearcher#searchLeaf()`, so it silently truncates and violates Design Invariant 3.
- A `Writeable` OpenSearch exception does NOT need exception-registry registration for its MESSAGE to reach the REST body. The type is lost across the transport, the message survives. Assert on message TEXT in ITs, never on the exception class name.
- `addRequestCircuitBreakerBytes(long)` is inherited protected from `AggregatorBase` (`AggregatorBase.java:169`). Release is AUTOMATIC in `AggregatorBase.close()` via `addWithoutBreaking(-requestBytesUsed)` — do not hand-release, but confirm no subclass overrides `close()`/`doClose()` without calling super. Charge in batches of 1024 (OpenSearch's `MultiBucketConsumer` probe cadence), never per row, and flush the final partial batch on EVERY exit path including the throw.
- `forcingOperator` is `RelNode.getRelTypeName()` computed by `StagePlanner` as the immediate parent of the cut (null when the cut IS the root), with a `[window]` qualifier appended for a Project/Calc holding a `RexOver` — otherwise the message blames a `LogicalProject`, which normally IS shard-local, and misleads. The qualifier reuses the single `StagePlanner.containsWindowFunction(RelNode)` that the placement pass uses, so classification and message cannot drift. Do NOT reverse-map RelNode classes to PPL command names like `eventstats`; that is not soundly derivable and the doc's example is illustrative of message SHAPE only.

## Shipping a coordinator-only fact to the shard: the wire-widening checklist
- Ask FIRST whether the shard can derive the fact from its own mapping/context. US-008's nested paths could (~15 lines, zero round-trip risk); US-009's forcing operator could not, because only the coordinator holds the plan.
- When you must ship it, widening `CalciteExecAggregationBuilder` requires ALL of: `writeTo`, the `StreamInput` ctor (same ORDER, same optional-ness), XContent output, the XContent PARSER, `equals`, `hashCode`, setter/getter, and a round-trip test asserting WHOLE-OBJECT equality for both the null and non-null case (`CalciteExecAggregationBuilderWireTest` is that test — extend it). A field missing from only the parser, or only `equals`, is completely invisible on a single-node test cluster.

## Raw `_search` integration tests must put `allow_partial_search_results=false` ON THE URL
- It defaults to TRUE. Without it, a shard-level exception returns HTTP 200 with a `_shards.failed` entry and partial results, so a fail-fast test passes by not throwing while proving nothing. The staged path sets it programmatically on `SearchRequest`, but a hand-built REST request in an IT does not inherit that.
- `TEST_INDEX_BANK` is 7 docs on a single shard, which makes small row budgets deterministic (`row_budget: 2` breaches at `gathered 3 rows`). That determinism is what lets an IT assert the EXACT message substring instead of a loose `contains("rows")`.

## Trusting test numbers: archive the XML, and read the skip messages
- `integTest` DELETES the whole `integ-test/build/test-results/integTest/` directory at the start of every invocation. Running classes in batches therefore destroys the earlier batches' XML, and any number reported from a wiped batch is unverifiable. Run every class in ONE invocation, or copy the XML out of `build/` immediately (`.sisyphus/handoff/<story>-xml/`). Combine with the existing rule: always `--rerun-tasks` and read counts from the XML, never from the Gradle exit code.
- A green class with a high skip count is a FINDING. Read the skip MESSAGES: `CalciteExplainIT` self-skips 76 of 266 tests via `assumeTrue("This test is only for when push down is enabled")`, so under the PoC posture it reports 0 failures while actually covering 186/266. Distinguish posture-induced assumption skips from inherited parent `@Ignore`s (e.g. `org.opensearch.sql.ppl.HeadCommandIT`, issue 703) before quoting any pass rate.
- When a story's deliverable is a TABLE of counts, machine-check it: every row must satisfy `tests - skipped == pass + fail-on-assertion + fail-on-ceiling`, and the per-cause annotation counts must sum to the failure total. A hand-summed footer is a defect site — the US-010 pass total was transcribed 332 for a true 333.
- When a bucket comes back EMPTY, state why in the report. `0 fail-on-ceiling` means nothing approached the budget, NOT that the ceiling works.

## Landing a measurement story without turning CI red
- A measurement story adds test classes that are EXPECTED to fail; the failures are the deliverable. Committing them red breaks the shared branch, deleting them destroys the reproducible harness. Resolution: commit them all, and put a class-level `@Ignore` on exactly the red ones whose reason states the measured failure count, the actual exception shapes, and the story ID that unblocks it. The unblocking story deletes one annotation as part of its acceptance. Precedent: `StagedCalcite{Top,Stats,Dedup}CommandIT` and `StagedCalcitePPLEventstatsIT` (US-010, unblocked by US-012/US-014/US-015).
- The posture-setting IT subclass pattern is: extend the parent, override `init()` to set `CALCITE_PUSHDOWN_ENABLED=false` and `CALCITE_FALLBACK_ALLOWED=false` as `transient` cluster settings, and `@After tearDown()` restoring BOTH to `null` before `super.tearDown()`. The restore is load-bearing — integTest shares one cluster. Canonical example: `integ-test/src/test/java/org/opensearch/sql/calcite/remote/StagedCalciteWhereCommandIT.java`.
- The design doc's per-class test counts are STALE (`stats` is 63 not 4, `top` is 9 not 5). Never gate on a count taken from the doc.

## A COORDINATOR THAT CANNOT RUN AN OPERATOR MAKES DESIGN INVARIANT 1 A LIE (US-014)
- Invariant 1 says absence of an optimization rule means the operator runs ON THE COORDINATOR. That is only true if the coordinator can actually execute it. `CoordinatorTreeExecutor`'s HEP program was missing `CoreRules.PROJECT_TO_LOGICAL_PROJECT_AND_WINDOW` while still running `FILTER_TO_CALC`/`PROJECT_TO_CALC`/`CALC_MERGE`, so a coordinator-side rank-filter window (`Project(ROW_NUMBER)` + `Filter(rn <= k)` + `Project`, which is what `top N f` lowers to) was merged into ONE `LogicalCalc` carrying a `RexOver` — and no rule converts such a Calc to ENUMERABLE. Volcano failed with `CannotPlanException: Missing conversion is LogicalCalc[convention: NONE -> ENUMERABLE]`. That single omission was the ENTIRE cause of all 9 `StagedCalciteTopCommandIT` failures, and it had been mis-attributed in the US-010 baseline to missing split rules ("unblocked by US-012 and US-014").
- THE WINDOW-EXTRACTION RULE MUST PRECEDE THE CALC RULES ON **BOTH** SIDES. The shard path (`CalciteExecAggregator.optimizeFragment`) has had the correct order since US-005 and the note "two optimizer passes are needed" was recorded then — but it was recorded as a fact about the SHARD, so the coordinator's copy of the same trio was never audited against it. When two execution paths run near-identical rule programs, diff them rule by rule; a pattern note scoped to one path will not protect the other. Same defect family as the promotion-path guard-parity rule below.
- REPRODUCE A COORDINATOR PLANNING FAILURE IN `CoordinatorTreeExecutorTest`, NOT IN AN IT. Building `Project(RexOver)` + `Filter` + `Project` over a gathered-rows scan reproduced the production `CannotPlanException` byte for byte in a unit test that needs no cluster, and it left a permanent regression test. The IT only told us 9 tests were red. Assert the RESULT (`rn <= 1` yields the single highest-count row), not merely that it stops throwing.

## Rule 2: ordered Sort+Fetch top-N, and why promotion ORDER is load-bearing (US-014)
- The rule fires when the node directly above the cut is a `Sort` with a NON-EMPTY collation, a `RexLiteral` fetch >= 0, and offset null-or-zero. The empty-vs-non-empty collation test is the whole boundary between rule 2 and US-013's rule 4 — one predicate separates them, so a change to either must re-read the other.
- UNLIKE MERGE_AGG AND LIMIT, THE COORDINATOR KEEPS THE ORIGINAL SORT. The cut is NOT promoted; the fragment gets a standard `LogicalSort(sameCollation, null, fetch)` and the coordinator's own Sort remains above the gathered rows as the authoritative final merge. That is the classic partial/final top-N shape and it is why tier 1 is a pure volume reduction: global top-n over the union of per-shard top-n IS global top-n, so a shard-local top-N can never discard a row the coordinator needed. Consequence for the guard-parity rule: the node `replaceSubtree` replaces here IS `cutNode`, so unlike the other two promotions the shared-subtree/join guard correctly names `cutNode`.
- `trySplitAggregate` MUST STAY AHEAD OF `trySplitTopN` IN `split()`, AND THIS IS A CORRECTNESS ORDERING, NOT A PREFERENCE. For `stats ... | sort N | head 3` the Sort+fetch sits ABOVE the Aggregate, so the aggregate promotion wins and the Sort stays on the coordinator (`explain_agg_script_timestamp_push.yaml` is the live case, MERGE_AGG with a `fetch=[3]` in its logical plan). A per-shard top-3 of PARTIAL aggregates would be silently wrong: a group whose global count is large can have a small per-shard partial and would be discarded before the merge. Rule 2 is only safe when the fetch applies to the SAME rows the shard emits.
- NO EARLY TERMINATION, DELIBERATELY, AND THIS IS THE OTHER HALF OF THE RULE-4 LESSON. Unless the index sort matches the requested order, the n-th smallest key is unknown until every matching document has been examined, so stopping at n collected docs would silently truncate (Design Invariant 3). `earlyTerminationLimit` stays null on this path; rule 4 sets it only because an UNORDERED fetch has no such dependency.
- "Bounded memory via a priority queue of size N" IS NOT ACHIEVABLE and asking for it misreads where the memory goes. calcite-linq4j 1.42.0 contains NO queue class at all (verified by listing the jar, not assumed), so `EnumerableLimitSort` sorts its whole input then takes n. It would buy nothing regardless: `CalciteExecAggregator.collect()` buffers every matching row BEFORE the fragment runs, so shard peak memory is already O(matching docs) whatever the fragment does. Registering `ENUMERABLE_LIMIT_SORT_RULE` (NOT part of `EnumerableRules.rules()` in 1.42.0) is still worth it as a plan-shape improvement, and the fused shape is what guarantees at most n rows are SHIPPED.
- TOP_N reduce is sort-then-truncate and is associative because the union of per-run top-n contains the global top-n. Direction specs go on the wire as `<Direction>:<NullDirection>` with UNSPECIFIED resolved to `direction.defaultNullDirection()` ON THE COORDINATOR, where Calcite's own default is available — the reduce side must never guess. Note `DESCENDING.defaultNullDirection()` is FIRST, not LAST. Null placement is ABSOLUTE and must NOT be flipped again by the descending flag, or nulls land at the wrong end.
