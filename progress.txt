# Codebase Patterns

Seeded from the design session on 2026-08-17. These are verified against source; trust them.

## Build and test commands
- Build (skip ITs): `./gradlew build -x :integ-test:integTest`
- Unit tests: `./gradlew test`
- All integration tests: `./gradlew :integ-test:integTest`
- Single IT class: `./gradlew :integ-test:integTest --tests "org.opensearch.sql.calcite.remote.CalciteDedupCommandIT"`
- Single IT method: `./gradlew :integ-test:integTest --tests "org.opensearch.sql.calcite.remote.CalciteExplainIT.testComplexDedup"`
- `-Dtests.security.manager=false` is already set in build.gradle.
- `:doctest:bootstrap` CANNOT run on this dev host: the repo venv is python3.7 and `doctest/sql-cli` pins `boto3==1.34.34`, which requires python>=3.8. `./gradlew build -x :integ-test:integTest` therefore FAILS on `:doctest:bootstrap` for reasons unrelated to any code change. Use `./gradlew build -x :integ-test:integTest -x :doctest:bootstrap -x :doctest:doctest` instead.
- Full Java build takes ~9 min cold; `./gradlew test` ~20s warm; `./gradlew spotlessCheck` ~35s.

## Plan-level limit already exists — do not add a second limit concept

## OpenSearch aggregation lifecycle constraints
- `InternalAggregation.reduce()` is called in batches of `batched_reduce_size` (default 512) by `QueryPhaseResultConsumer.PendingReduces`. It MUST be associative. There is no opt-out.
- `mustReduceOnSingleInternalAgg()` only forces reduce() when a single shard returned; it does NOT disable batching.
- Therefore the wire type must carry UNFINALIZED accumulator state (avg ships {sum, count}, never an average).
- Batched reduce lowers peak memory only when the combine reduces volume. CONCAT gains nothing.
- `Aggregator.collect()` can read _source via `SearchContext.lookup().getLeafSearchLookup(ctx).source()`, and this works under `size: 0` because it is independent of the fetch phase.
- `size: 0` sets `hasTopDocs=false`, skipping the fetch phase, so no reader context and no PIT is created.
- `CollectionTerminatedException` terminates the CURRENT LEAF ONLY — it is caught by `ContextIndexSearcher#searchLeaf()` and the leaf loop continues. Stopping a whole shard needs a shard-global counter plus a guard in `getLeafCollector()`.
- `allow_partial_search_results` defaults to TRUE. Every request this PoC builds must set `allowPartialSearchResults(false)`, or a budget breach returns HTTP 200 with partial results.
- Transport ceiling from data node to coordinator is 30% of JVM heap, hardcoded in `TcpTransport`. There is no `transport.max_message_size` setting.

## Calcite facts
- Aggregate splitting bottoms out per function: `SqlSplittableAggFunction` with `CountSplitter`, `SumSplitter`, `Sum0Splitter`, `SelfSplitter`. If `unwrap(SqlSplittableAggFunction.class)` returns null the call cannot be split.
- There is no generic mechanism to split Window, Sort, Join, or Distinct. The standard fallback is gather to SINGLETON.
- Limit-pushability is per-operator: exact below Project/Calc, merges with Sort into top-N, exact per-branch for Union ALL. NOT below Filter, Aggregate, general Window, Join, or Union DISTINCT.
- PPL `dedup` already lowers to `ROW_NUMBER() OVER (PARTITION BY ...)` plus a `<= k` filter — no custom operator is involved on the Calcite path.

## Custom logical operators (audit result, US-001)
- Only three custom logical RelNodes exist on the Calcite path:
  - `LogicalSystemLimit` (`core/.../calcite/plan/rel/LogicalSystemLimit.java:25`, a `Sort` subclass, present in every plan)
  - `LogicalDedup` (`core/.../calcite/plan/rel/LogicalDedup.java:20`, transient during HEP, lowered by `PPLDedupConvertRule`)
  - `LogicalGraphLookup` (`core/.../calcite/plan/rel/LogicalGraphLookup.java:22`, irreducible, from `graphLookup`, becomes `CalciteEnumerableGraphLookup`)
- `TimeWindow` (`core/.../calcite/plan/TimeWindow.java:15`) is dead code never instantiated.
- Every other PPL command produces only standard Calcite operators.
- `dedup` uses `ROW_NUMBER` exclusively (never `RANK`/`DENSE_RANK`) via `CalciteRelNodeVisitor.visitDedupe()` (line 2208) and `PPLDedupConvertRule.buildDedupNotNull()`/`buildDedupOrNull()`.
- `dedup consecutive=true` throws `CalciteUnsupportedException` (`CalciteRelNodeVisitor.java:2217`).

## Design invariants — do not violate
1. The split must be TOTAL over RelNode. Absence of an optimization rule means the operator runs on the coordinator. Never reject a plan.
2. Never emit a Painless script query. If a predicate is not index-accelerable, leave it as a residual Filter in the fragment.
3. Never silently truncate. Either the limit is provably pushable, or the budget refuses the query with a diagnosable error.
4. One search request per OpenSearchIndexScan. Never create a PIT, scroll, or search_after on this path.
5. Standard Calcite operators only.

Full design: `docs/dev/poc-staged-calcite-exec-design.md`

## The stage split: StagePlanner (US-007)
- `opensearch/src/main/java/org/opensearch/sql/opensearch/stage/StagePlanner.java` — `static StagePlan split(RelNode root)`. Never throws, never returns null, for any RelNode tree.
- MODULE DEVIATION, and it is permanent: the design doc assigns StagePlanner to `core`, but `core/build.gradle` has NO dependency on `:opensearch` while StagePlanner must reference `CombineDescriptor`, `RelFragmentCodec`, and `AbstractCalciteIndexScan` — all in `opensearch`. It therefore lives in `opensearch`. Dependency direction is `opensearch --api--> core`, one way only. Any future story that the doc places in `core` but which touches the stage package has the same problem.
- Shard-scan recognition is the single package-private predicate `StagePlanner.isShardScan(RelNode)` → `node instanceof AbstractCalciteIndexScan`. Widen THERE, nowhere else. Do NOT make every `TableScan` SHARD_LOCAL — that would falsely claim non-OpenSearch tables are shard-distributed.
- Placement is one memoized bottom-up pass into an `IdentityHashMap<RelNode, Boolean>`, then a top-down walk reading the memo to find the highest SHARD_LOCAL node. Use IDENTITY maps for RelNode keys throughout — `AbstractRelNode` does not override `equals`/`hashCode`, so `equals` is reference equality today, but relying on that implicitly is fragile.
- A `Project` or `Calc` containing a `RexOver` is NEEDS_GATHER, not SHARD_LOCAL. PPL lowers window functions (`dedup`, `eventstats`) into a `LogicalProject` holding `ROW_NUMBER() OVER (...)`, and per-shard numbering restarts at 1, so shipping it shard-local and CONCAT-ing is SILENTLY WRONG. Guards: `RexOver.containsOver(project.getProjects(), null)` and `RexOver.containsOver(calc.getProgram())`. A `Filter` needs no such guard — the Calcite 1.42.0 validator rejects a `RexOver` in a filter condition. Partial window evaluation is US-015's `RANK_LIMIT` rule and is the ONLY correct way to make windows shard-local.
- The shardFragment's leaf is NOT the `AbstractCalciteIndexScan`. `split()` replaces it with a plain `LogicalTableScan` over `[RelFragmentCodec.SCHEMA_NAME, <indexName>]` carrying the SAME row type, so `RelFragmentCodec.serialize(shardFragment)` round-trips. The original scan is preserved on `StagePlan.shardScan()` so a later story can read index name, pushed-down DSL, and field list without re-walking the tree.
- The coordinatorTree replaces the whole cut subtree with a gathered-rows `LogicalTableScan` whose row type is the CUT NODE's row type, backed by `RelFragmentCodec.ShardRowSourceTable` parameterized with `StagePlanner.GATHERED_ROWS_STASH_KEY` = `"calcite_exec.gathered_rows"` (table name `_gathered_rows`). `ShardRowSourceTable` now has a 2-arg ctor taking a stash key; the 1-arg ctor still defaults to `SHARD_ROWS_STASH_KEY`, so the US-005 shard path is untouched.
- ZERO or MORE THAN ONE `AbstractCalciteIndexScan` (e.g. a join across two indices) has no single gather boundary, so `split()` returns a coordinator-only `StagePlan`: `staged()==false`, `coordinatorTree()==root` untouched, `shardFragment()`/`shardScan()`/`combine()` null. This preserves Design Invariant 1 (never reject a plan). Multi-scan staging is deliberately out of PoC scope. Callers MUST check `staged()`.
- `LogicalSystemLimit` is a `Sort` subclass, so the generic floor makes it NEEDS_GATHER and it lands on the coordinator. That is correct for the floor; US-013/US-014 own limit pushdown. Do not special-case it.
- Tree rebuilds use `node.copy(node.getTraitSet(), newInputs)`. Safe for `LogicalSystemLimit`, Project, Filter, Calc because the replacement leaf's row type is identical to the original's, so no `RexInputRef` shifts index or type. Preserve row type exactly whenever swapping a leaf.

## Custom aggregation: calcite_exec (US-002)
- Aggregation type name: `calcite_exec`
- Package: `org.opensearch.sql.opensearch.stage` (in `opensearch` module)
- Classes:
  - `CombineDescriptor` — enum of reduce modes (CONCAT, MERGE_AGG, LIMIT, TOP_N, RANK_LIMIT) plus parameters
  - `CalciteExecAggregationBuilder` — XContent parser + Writeable builder; fields: plan, fields, combine, rowBudget
  - `CalciteExecAggregatorFactory` — creates aggregator via `createInternal(SearchContext, Aggregator, CardinalityUpperBound, Map<String,Object>)`
  - `CalciteExecAggregator` — extends MetricsAggregator; collects docs, executes fragment, emits InternalCalciteExec
  - `InternalCalciteExec` — InternalAggregation; carries rows + combine descriptor; reduce() applies combine mode
- Registration: `SQLPlugin.getAggregations()` (SQLPlugin now implements SearchPlugin)
- Module-visibility rule: `opensearch` module has the full opensearch server jar (`opensearch/build.gradle:36`); `core` has only `opensearch-core`. Any class touching InternalAggregation, AggregatorFactory, MetricsAggregator, or SearchContext must live in `opensearch` (or `plugin`), never `core`.
- CombineDescriptor modes: CONCAT (US-002), MERGE_AGG (US-012), LIMIT (US-013), TOP_N (US-014), RANK_LIMIT (US-015)

## Fragment codec: RelFragmentCodec (US-003)
- `opensearch/src/main/java/org/opensearch/sql/opensearch/stage/RelFragmentCodec.java` — `serialize(RelNode) -> base64 RelJson` and `deserialize(base64, indexName, List<FieldDescriptor>) -> RelNode`.
- Calcite 1.42.0 signatures that make custom RelJson injection possible: `RelJsonWriter(JsonBuilder, UnaryOperator<RelJson>)` and `RelJsonReader(RelOptCluster, RelOptSchema, Schema, UnaryOperator<RelJson>)`. Use these to inject `ExtendedRelJson` so PPL operators round-trip. Plain `RelJson` would silently lose them.
- `RelJsonSerializer.getPplSqlOperatorTable()` is now `public static` (backing field is `volatile`, so the double-checked-locking singleton is correct). ALWAYS reuse it — never re-chain PPLBuiltinOperators + SqlStdOperatorTable + OperatorTable + SqlLibrary by hand.
- `ExtendedRelJson.create(jsonBuilder)` leaves `inputTranslator = null`, and `withOperatorTable()` NPEs on a null translator because the 3-arg ctor `requireNonNull`s it. So on the read path you MUST chain `.withInputTranslator(...)` before `.withOperatorTable(...)`. The translator itself is never invoked — `RelJsonReader` resolves input refs through its own `RelInput` — so it should throw `UnsupportedOperationException` rather than fabricate refs. An earlier draft fabricated `SqlTypeName.ANY` refs, which would have been silently wrong if ever reached.
- Table path convention is `[OpenSearch, <indexName>]` (`RelFragmentCodec.SCHEMA_NAME`). The SAME path must be registered on both the serialization and the deserialization side or `RelOptUtil.toString()` will not match.
- `RelFragmentCodec.SHARD_ROWS_STASH_KEY` = `"calcite_exec.shard_rows"`. `ShardRowSourceTable` is a `ScannableTable` that reads `List<Object[]>` from `DataContext.get(SHARD_ROWS_STASH_KEY)` and returns an empty enumerable when absent. US-005 injects rows here.

## Wire type strings are OPENSEARCH type names, not SqlTypeName names
- `CalciteExecAggregationBuilder.FieldDescriptor.type` is a free-form `String` carrying an OpenSearch field type. The authoritative example at `docs/dev/poc-staged-calcite-exec-design.md:270-272` is `{"name":"account_number","type":"long"}` / `{"name":"gender","type":"keyword"}`.
- Therefore `SqlTypeName.valueOf(fd.getType())` ALWAYS throws on real wire data. `RelFragmentCodec` owns the mapping: keyword/text→VARCHAR, long→BIGINT, integer→INTEGER, double→DOUBLE, float→REAL, boolean→BOOLEAN, date→TIMESTAMP; anything else throws naming the field and the type. Extend that map when a story needs a new type — do not add a second mapping elsewhere.
- Do NOT reuse `OpenSearchTypeFactory.convertExprTypeToRelDataType` for this: it takes an `ExprType` object rather than a string, and returns UDT wrapper types (ExprDateType, ExprTimeStampType, …) for date/time/timestamp/ip that do not survive the RelJson round-trip.
- Lesson: write unit tests against the REAL wire spellings from the design doc. The first draft's tests fed `"BIGINT"`/`"VARCHAR"` and passed green while the production path was broken for every actual caller.

## Shard row materialization: ShardRowReader (US-004)
- `opensearch/src/main/java/org/opensearch/sql/opensearch/stage/ShardRowReader.java` owns ALL field-value extraction for the shard fragment. One `FieldReader` closure per requested field, built once per Lucene leaf in `CalciteExecAggregator.getLeafCollector()`; `readRow(doc)` returns an `Object[]` with exactly one slot per requested field, in request order, `null` when the field is absent from a doc.
- Type dispatch keys off the SAME OpenSearch type strings as the wire (`keyword`, `long`, `integer`, `double`, `float`, `boolean`, `date`, `text`) — see the wire-type note above. Keep this switch and `RelFragmentCodec`'s SqlTypeName map in sync: adding a type needs BOTH.
- doc_values access uses `advanceExact(doc)`, never `advance()`. `advanceExact` is stateful per reader instance, so a reader MUST be created per leaf — never cache a `FieldReader` across `getLeafCollector()` calls or docIDs from a later leaf will silently miss.
- Encoding decisions in the Object[]: keyword → `String` (BytesRef.utf8ToString), long/date → `Long` (date is epoch millis), integer → `Integer`, double → `Double` via `NumericUtils.sortableLongToDouble`, float → `Float` via `sortableIntToFloat`, boolean → `Boolean` from 0/1. Numeric doc_values are stored sortable-encoded — reading the raw long for a double/float gives garbage.
- `text` (and any field with no doc_values) falls back to `_source`. `ShardRowReader.create()` does NOT position the `SourceLookup`; the CALLER must call `sourceLookup.setSegmentAndDocument(ctx, doc)` before `readRow(doc)`. Obtain the lookup via `SearchContext.lookup().getLeafSearchLookup(ctx).source()` — this works under `size: 0` because it is independent of the fetch phase.
- `InternalCalciteExec` carries `rowsCollected` and `rowsEmitted` as VLongs (both in `writeTo`/StreamInput ctor/XContent/equals/hashCode). They are currently always equal; they diverge only once US-009 enforces the row budget.

## Shard fragment execution: the compile-and-run pipeline (US-005)
- `CalciteExecAggregator.buildAggregation()` is the single execution entry point on the shard. One code path only: `RelFragmentCodec.deserialize` -> HEP pass -> Volcano pass -> Janino `Bindable` -> `bind(DataContext)` -> drain. There is deliberately NO bypass, no sentinel plan value, and no catch-and-return-raw-rows fallback. A bad plan MUST fail loudly. Do not reintroduce one to keep an older test green — fix the test instead.
- Reaching a `Bindable` needs TWO optimizer passes, not one:
  1. HEP: `PROJECT_TO_LOGICAL_PROJECT_AND_WINDOW`, `FILTER_TO_CALC`, `PROJECT_TO_CALC`, `CALC_MERGE`.
  2. Volcano: convert to `EnumerableConvention`, then `EnumerableInterpretable.toBindable(ImmutableMap.of(), null, rel, Prefer.ARRAY)`.
  Why the HEP pass is mandatory: `EnumerableProject.implement()` throws `UnsupportedOperationException` under `Prefer.ARRAY`, so Projects must become Calcs; and a `RexOver` sitting inside a `LogicalProject` NEVER becomes an `EnumerableWindow` unless `ProjectToWindowRule` extracts it first. A single Volcano pass silently fails on both.
- The `SparkHandler` argument to `toBindable` is `@Nullable` and `null` is the CORRECT value — that is precisely the branch that Janino-compiles. Passing a handler would route to Spark.
- `CalciteClassLoaderHelper.withCalciteClassLoader(Callable, callerClass)` (in `core`, visible from `opensearch`) MUST wrap the whole compile+bind+drain block. Janino resolves classes through `Thread.currentThread().getContextClassLoader()` (CALCITE-3745); without the wrapper the generated code cannot see plugin classes on a data node. The helper restores the loader in a `finally`.
- `DataContexts.of(Map)` is NOT usable here: generated `EnumerableTableScan` code calls `root.getRootSchema().getSubSchema("OpenSearch").getTable(...)` at runtime and `DataContexts.of` leaves `rootSchema` null. Use a custom `DataContext` serving BOTH the root schema AND the `SHARD_ROWS_STASH_KEY` slot. It currently returns null for `DataContext.Variable.UTC_TIMESTAMP` — a fragment containing `NOW()`/`CURRENT_TIMESTAMP` will NPE in `UserDefinedFunctionUtils.restoreFunctionProperties:168`. Whichever story first ships a temporal fragment must fix that, and must verify the unit (millis vs nanos) against Calcite 1.42 rather than guessing.
- `Prefer.ARRAY` returns a BARE SCALAR, not an `Object[]`, when the output row type has exactly one field. Any drain loop needs that guard or single-column fragments blow up on the cast.
- The row buffer is `List<Object[]>` (matching `ShardRowReader.readRow` and the stash contract), never `List<List<Object>>`.
- `RelFragmentCodec`'s deserialization planner registers `ConventionTraitDef.INSTANCE` and `RelCollationTraitDef.INSTANCE`. Both are required for the EnumerableConvention conversion; a cluster without them cannot be optimized at all.
- `executeFragment(...)` is package-private static precisely so unit tests can drive compile-and-run with a literal `List<Object[]>` and no aggregation framework. Prefer that over an IT when testing plan shapes.
- Do NOT route shard execution through a JDBC `Connection`/`RelRunner` (`CalciteToolsHelper.OpenSearchRelRunners`). That is the coordinator path; the data node compiles a `Bindable` directly.

## Pushdown and PredicateAnalyzer
- `PredicateAnalyzer` lives at `opensearch/src/main/java/org/opensearch/sql/opensearch/request/PredicateAnalyzer.java` and is a `RexVisitorImpl<QueryBuilder>`. Entry points: `analyze(RexNode)` (returns `QueryBuilder` or throws) and `analyzeExpression(RexNode)` (same, no script fallback).
- The predicate path can NO LONGER emit a Painless script. The script-query emission path (`ScriptQueryExpression` in `Visitor.tryAnalyzeOperand` and the `catch`-and-wrap in `analyzeExpression`) is deleted as of US-006.
- Pushdown refusal is signalled by `PredicateAnalyzerException` or `ExpressionNotAnalyzableException`. This is SAFE because:
  - `FilterIndexScanRule` only calls `call.transformTo()` on a non-null result from `PredicateAnalyzer` — a thrown exception means the Filter stays intact in the Calcite plan.
  - `AggregateIndexScanRule` only calls `call.transformTo()` when `CalciteLogicalIndexScan.pushDownAggregate()` returns non-null; that method catches `PredicateAnalyzerException`, logs at debug, and returns null.
- DANGER: nested-field aggregations REQUIRE pushdown and have no Calcite fallback. If a filter on a nested-field aggregation is refused by `PredicateAnalyzer`, the query fails with HTTP 500 PLANNING_ERROR. Any future narrowing of pushability MUST run `CalciteExplainIT` (all 266 tests) as a regression gate.
- The only remaining `new ScriptQueryExpression` in main is in `AggregateAnalyzer` (~line 187, for aggregation MEASURE scripts) and the sort path (`SortAnalyzer`). Neither is a predicate.
- Explain goldens live under `integ-test/src/test/resources/expectedOutput/calcite/` and are re-baselined by editing the YAML/JSON files directly.
